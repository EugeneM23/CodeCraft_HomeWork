# Правила производительности

**Дата:** 2026-11-17
**Статус:** действует. Согласовано с пользователем 2026-11-17.
**Владелец:** команда «Производительность и порядок». Правки бюджетов — только с одобрения пользователя.
**Проверяет:** агент `perf-check` (`/perf-check`, см. `Docs/Rules/README.md`).

## 1. Цель

**60 FPS на среднем ПК:** 1920×1080, качество High. Ориентир — Ryzen 5 3600 или i5-10400, 16 ГБ, GTX 1660 Super или RTX 3060. Кадр на целевом ПК — 16.6 мс.

Целевого ПК у нас нет. Замеры снимаем в редакторе на машине разработки: RTX 5090 Laptop. Поэтому бюджеты ниже пересчитаны с запасом:

- CPU машины разработки примерно в 2–2.5 раза быстрее целевого. В редакторе, кроме того, сама игра идёт медленнее, чем в сборке. Бюджет главного потока берём в 3 раза меньше кадра цели: **5 мс**.
- GPU быстрее примерно в 4 раза. Бюджет GPU — **4 мс**.

Когда появится сборка на целевом железе, цифры уточняем замером там.

## 2. Бюджеты

Все цифры относятся к машине разработки: редактор, Play, VoxelSandbox. Порядок замера — в разделе 4.

### Кадр

| Метрика | Бюджет | Как считается |
|---|---|---|
| **PlayerLoop**, среднее | **≤ 5.0 мс** | кадр самой игры без редактора |
| PlayerLoop, p95 | ≤ 6.5 мс | |
| PlayerLoop, худший кадр сценария | ≤ 16 мс | в том числе кадр взрыва и кадр давки |
| Кадров PlayerLoop > 16.6 мс в простое и езде | 0 | |
| GPU Frame Time, среднее | ≤ 4.0 мс | |
| **GC-аллокации в PlayerLoop** в простое и езде | **0 Б в кадре** | сумма GC.Alloc под PlayerLoop. Аллокации редактора не считаются |
| GC-аллокации в кадре события (взрыв, давка, спавн) | ≤ 4 КБ | разовый пик, не каждый кадр |

### Подсистемы (внутри PlayerLoop, среднее)

| Подсистема | Бюджет | Маркеры профайлера |
|---|---|---|
| Воксели (главный поток) | ≤ 1.0 мс | `VoxelWorld.*`, `VoxelBody.*`, `VoxelDebris.*`, хук `EarlyUpdate` вокселей |
| Физика | ≤ 1.0 мс | `FixedUpdate.PhysicsFixedUpdate` |
| Скрипты геймплея без вокселей | ≤ 1.0 мс | `Update.ScriptRunBehaviourUpdate`, `PreLateUpdate.ScriptRunBehaviourLateUpdate`, `FixedUpdate.ScriptRunBehaviourFixedUpdate` минус воксели |
| Отправка рендера | ≤ 1.5 мс | `PostLateUpdate.FinishFrameRendering` |
| Остальное (анимация, UI, звук, частицы) | ≤ 0.5 мс | PlayerLoop минус всё выше |

### Рендер (в кадре, среднее)

| Метрика | Бюджет |
|---|---|
| Batches | ≤ 1000 |
| SetPass calls | ≤ 300 |
| Shadow casters | ≤ 500 |
| Треугольники | ≤ 2 млн |

### Что считается нарушением

- **Выход за бюджет блокирует влитие ветки.** Тимлид не вливает её в `game/develop`, пока выход не исправлен или пользователь не дал исключение. Исключение записывается в отчёт агента с датой и причиной.
- **Рост больше 10 % против прошлого замера**, даже внутри бюджета, — предупреждение. Ветку можно влить, но причину роста надо назвать в отчёте команды.
- Новые GC-аллокации в простое и езде — нарушение при любом размере.

## 3. Сценарии замера

| Сценарий | Сцена | Что происходит | Длительность |
|---|---|---|---|
| **idle** | VoxelSandbox | танк стоит на старте, авиаудар выключен | 4 с |
| **drive** | VoxelSandbox | танк едет по дороге: сначала вперёд, потом назад, смена каждые 3 с, газ 1, руль 0. Авиаудар выключен | 8 с |
| **airstrike** | VoxelSandbox | танк стоит. Каждую секунду `VoxelAirStrike.Explode` в точке на земле в 12–16 м от танка, 6 взрывов | 6.5 с |
| **crush** | VoxelSandbox | ближайший Regax ставится на землю в 8 м перед танком, танк едет на него с газом 1 | 4 с |
| horde | уровень с ордой | появится вместе с ордой (команда AI) | 8 с |
| menu | MainMenu, Hangar | появится вместе с меню (команда меню) | 4 с |

- Танк стартует у x −34, а край карты — x −40. Поэтому танк всегда сначала едет вперёд.
- Авиаудар по таймеру в сценариях выключен (`VoxelAirStrike._on = false`): взрывы бывают только там, где их вызывает сценарий. Так замеры повторяемы.
- Сценарии орды и меню добавляет команда, которая делает эту часть игры. Сценарий — это шаг в `Tools/PerfCheck/Bench/` и строка в этой таблице.

## 4. Порядок замера

1. **Редактор.** Замер снимаем в редакторе, у которого `projectPath` — проверяемая рабочая копия. Для `game/develop` это основной редактор. Действуют правила общего редактора: не перекомпилировать и не делать Refresh в Play, не сохранять чужие сцены, не запускать и не останавливать Play без согласия того, кто сейчас в нём играет.
2. **Компиляция и Burst.** После любой компиляции Burst-задачи какое-то время идут в Mono. Замер начинается не раньше чем через **8 с** после входа в Play. Сценарий проверяет, что `BurstCompiler.IsEnabled`.
3. **Окна.** В Play включён Maximize On Play, или Scene view закрыт. Scene view рисует сцену второй раз и стоит 2–3.5 мс главного потока. Если он открыт, «Main Thread» в отчёте помечается как «со Scene view». PlayerLoop от Scene view не зависит.
4. **Инструмент.** `Tools/PerfCheck/Bench/perf_bench.cs` через `unity cmd script eval --file` — **одним вызовом**. Вызов ставит сценарии по очереди и возвращается сразу. Результат забирается вторым вызовом, `perf_bench_read.cs`. Танк ведётся через `Application.onBeforeRender`, после того как контроллер ввода обнулил газ с клавиатуры.
5. **Что пишется.**
   - `ProfilerRecorder` «PlayerLoop», «Main Thread», «GPU Frame Time», Batches, SetPass, Triangles, Shadow Casters. Recorder создаётся в начале каждого сценария, не в первые секунды Play.
   - Профайлер редактора (`ProfilerDriver`, `HierarchyFrameDataView`) — время подсистем и GC.Alloc под PlayerLoop. Профайлер включается на время замера и возвращается в прежнее состояние.
   - Для каждого сценария: среднее, p50, p95, худший кадр, число кадров > 16.6 мс.
6. **Повтор.** Если результат вышел за бюджет или вырос больше чем на 10 %, сценарий прогоняется второй раз. В отчёт идёт лучший из двух прогонов, разброс указывается.
7. **История.** Каждый замер добавляется строкой в `Docs/Reports/perf-history.jsonl`. Отчёт сравнивает с последней строкой той же ветки, а для веток команд — с последней строкой `game/develop`.

## 5. Правила кода

Правила обязательны для нового и изменённого кода. Нарушения в старом коде прототипа агент записывает в отчёт как долг. Долг должен только уменьшаться. Ветку блокируют только нарушения в строках, которые она добавила или изменила.

### Тик

- **Геймплей тикает через GameLoop** (`IGameLoop` модуля GameLoop), а не через `Update`, `LateUpdate` и `FixedUpdate` у `MonoBehaviour`. Тогда пауза его останавливает. Atomic-сущности тикают через свой мир, а мир тикает через GameLoop.
  - Правило вступает в силу, когда команда ядра вольёт модуль GameLoop. До этого — `IEntityTick`, `IEntityFixedTick`, `IEntityLateTick` у Atomic-сущностей.
  - `Update` разрешён: в редакторских инструментах, в демо и тестах, в ядре модулей из `Assets/Modules`, а также в коде, которому нужна работа и во время паузы (меню, звук UI). Последний случай помечается в конце строки комментарием `// perf-ok: ticks during pause (<что>)`. Тот же `// perf-ok: <почему>` снимает любое правило кода с одной строки, а агент проверяет, что причина правдоподобна.
- Пустые `Update`, `Start` и `OnGUI` удаляются: Unity вызывает их и пустыми.

### Аллокации

- **В тике ноль аллокаций.** «Тик» — это `Tick`, `FixedTick`, `LateTick`, `Update` и всё, что вызывается из них каждый кадр. В тике нельзя:
  - LINQ (`using System.Linq` в рантайм-коде не нужен вообще);
  - `new` ссылочных типов, массивов, `List`, `Dictionary`, делегатов и лямбд с захватом;
  - конкатенацию и интерполяцию строк, `ToString()`;
  - `foreach` по интерфейсу (`IEnumerable<T>`, `IList<T>`): он боксит перечислитель;
  - `GetComponent` и `Find*`: компоненты кэшируются в `Init` или `Awake`;
  - `Camera.main` в тике: кэшировать;
  - `GetBehaviours()`, `GetBehaviours<T>()` и `GetBehaviourEnumerator()` у Atomic-сущности. Вместо них `BehaviourCount` + `GetBehaviourAt(i)` или `CopyBehaviours(buffer)`;
  - физические запросы без `NonAlloc` (`RaycastAll`, `OverlapSphere`): нужны `RaycastNonAlloc`, `OverlapSphereNonAlloc` и т. п. с буфером, выделенным заранее;
  - `ValueKey` значимого типа в Atomic: он боксит. Ключи — интерфейсы элементов (`IValue<float>`, `IVariable<Vector3>`), см. `Docs/AtomicGuide/01-tutorials.md`.
- Текст в HUD и UI пересобирается не чаще 4 раз в секунду или по изменению значения. Для чисел — `TMP_Text.SetText(format, value)` без строки.

### Пулы

- **Всё, что появляется в бою больше одного раза, берётся из пула:** снаряды, эффекты, обломки, монстры, декали. `Instantiate` и `Destroy` в бою запрещены. Пул — `EntityPrefabPool` или `GameFactory`.
- Пул прогревается при загрузке уровня, а не на первом выстреле. Бюджет прогрева — не больше 2 мс в кадре.
- Пул без расширения (`ExpandMode.NoExpand`) — там, где лимит известен. Где неизвестен — `ExpandByDoubling`, не `ExpandByOne`.

### Массовые вычисления

- Всё, что обходит больше ~1000 элементов в кадре (воксели, обломки, орда, частицы своего движка), — Burst-задача (`IJob`, `IJobParallelFor`) над `NativeArray`.
- Задача ставится в кадре и забирается в начале следующего (хук в `EarlyUpdate`, как у `VoxelWorld`), а не ожидается тут же через `Complete()`. Ожидание в том же кадре допустимо, только если результат нужен сейчас и это записано комментарием.
- `[BurstCompile(DisableSafetyChecks = true)]` ставится только на горячие задачи, проверенные в Play с проверками безопасности.
- Отрисовка тысяч одинаковых объектов — инстансингом (`DrawMeshInstanced`, `RenderMeshInstanced`, procedural), не отдельными GameObject.

### Рендер

- Новый материал по возможности использует уже существующий шейдер, а варианты шейдера не плодятся ключевыми словами без нужды.
- Мелкие и плоские объекты не отбрасывают тень. Тень включается, только когда её видно.
- Новые источники света в бою — без теней и с ограниченной `range`. Вспышки на вокселях идут через `VoxelFlash`, а не через `Light`.

### Замер своими силами

- Новая тяжёлая подсистема (больше 0.2 мс в кадре) заводит `ProfilerMarker` с именем `<Подсистема>.<Шаг>`, например `Horde.Simulate`. Тогда её время видно в отчёте агента отдельной строкой.
- Команда, которая меняет горячий путь, прикладывает к отчёту тимлиду замер «до и после» по сценариям из раздела 3.
