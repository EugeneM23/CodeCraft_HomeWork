# Воксельная танковая игра: общий план производства

**Дата:** 2026-11-17
**Ветка интеграции:** `game/develop` (базовый коммит прототипа `126882f11`)
**Тимлид:** сессия «Воксельная игра: план разработки». Делит работу, принимает отчёты команд, показывает результаты пользователю, вливает ветки. Команды пишут ему через `SendMessage` по имени сессии.

## 1. Цель

Превратить прототип VoxelSandbox (танк в воксельном мире, разрушение, грязь, монстры Regax) в игру для ПК.

**Первая веха — сквозной играбельный цикл:**
запуск → главное меню → ангар → выбор уровня → бой в воксельном уровне (танк, Regax, орда) → итоги и награда → магазин → улучшение танка → сохранение прогресса.

Качество первой вехи — прототипное: всё работает от начала до конца, финального арта нет.

## 2. Решения по стеку

| Тема | Решение | Почему, что отвергли |
|---|---|---|
| Платформа | ПК, клавиатура и мышь. Геймпад позже | Уровень качества Mobile остаётся в проекте, но телефоны не цель |
| Движок | Unity **6000.3.28f1** (6.3 LTS) | Долгая поддержка. Ближе к 6000.5.6f1, на которой написаны модули Platformer, чем наша 6000.0.38f1. 6.5 отвергли: не LTS |
| Рендер | **URP** | Built-in не развивается. Переходим, пока своих шейдеров мало: 7 файлов и 2 Shader Graph. Условие: VoxelSandbox на URP выглядит как на Built-in, пользователь одобряет скриншоты «до и после» |
| Основа кода | **Atomic 3.0** (Elements, Entities, Events, генераторы) | На нём весь геймплей. Есть свой гайд, сверенный с исходниками: `Docs/AtomicGuide` |
| Тяжёлые системы | **Burst + Jobs + Collections + Mathematics** | Уже держат воксели, обломки, дым, грязь и дождь |
| Unity Entities (ECS) | **Не вводим** | Второй мир сущностей, своя физика, нет анимации, все модули Platformer на MonoBehaviour. Вернёмся, только если орда упрётся в предел и замер это покажет, и тогда для одной подсистемы |
| Орды монстров | Подсистема на Jobs: данные в `NativeArray`, отрисовка инстансингом на GPU с запечённой анимацией. Для остальной игры орда — одна Atomic-сущность | Так же сделаны обломки (`VoxelDebris`) |
| Сборка сервисов | **AppContext** — Atomic-сущность на всю игру. Сервисы — её значения со сгенерированным API, инсталлеры `MonoEntityInstaller<AppContext>` | ServiceLocator отвергли: второй способ связки рядом с контекстами. DI-контейнера нет ни у нас, ни в модулях |
| Слои | AppContext (вся игра) → GameContext (уровень) → сущности | |
| UI | **uGUI + TextMeshPro + ScreenStack** | ScreenStack из Platformer построен на uGUI |
| Ввод | **Input System**: actions, переназначение клавиш в настройках | Сейчас код читает старый `Input` |
| Игрок | В первой версии **всегда в танке** | Пеший режим, способности, баффы, гранаты, вертолёт и туман войны уходят. Они остаются в git, в базовом коммите |
| Разрушение | Только воксели | RayFire и `DestructibleWalls` уходят |
| Модули Platformer | Копия в `Assets/Modules/<Name>` вместе с `package.json` и asmdef. Ядро модуля правим только ради исправления ошибок, всё про нашу игру кладём в отдельные сборки-адаптеры | Тогда новую версию модуля можно перенести заново |
| Git | Код и документы коммитятся в ветках команд и вливаются в `game/develop` после одобрения пользователя | Правило «коммитим только документы» действовало на старых ветках |

```
Assets/

  Game/
    Scripts/
      App/                   AppContext, поток игры, загрузка уровней, инсталлеры       ядро

      Features/<Фича>/       игровые фичи: танк, камеры, здоровье, грязь...             по фиче
      Features/AI/           адаптеры AIKit, мозги монстров                             AI
    Horde/                   подсистема орды: Runtime (Burst), Tests, своя сборка       AI
    Voxels/                  воксельный модуль; Editor/Voxelizer — инструмент           вокселизатор
    Audio/Banks/             банки звуков                                               звук
    Scenes/                  Boot, MainMenu, Hangar, Levels/<Уровень>/...               ядро, меню
Docs/
  superpowers/specs, plans/  спецификации и планы команд
  Game/                      геймдизайн-документ                                        геймдизайн
  Rules/                     правила производительности и порядка                      производительность
.claude/agents/              агент-проверяющий                                          производительность
```

Подробные правила нейминга и папок пишет команда производительности и порядка (`Docs/Rules/Project.md`). До них действует раскладка выше.

**Ключи сущностей.** Каждая команда объявляет свои ключи в собственном файле `<Команда>API.cs` с атрибутом `[EntityExtensionsAPI]` внутри своей папки, по образцу `AbilityAPI.cs` и `GameContextAPI.cs`. Общий `Scripts/Declarations/EntityAPI.cs` правит только команда чистки. Через этот файл раньше чужая работа попадала в коммиты.

**Пакеты и настройки.** `Packages/manifest.json` и `ProjectSettings/` меняют только команды Unity 6.3, рендера и ядра. Остальные просят тимлида. Конфликты в них при слиянии решает тимлид.

## 6. Порядок

**Волна 1 (сразу):** Unity 6.3, геймдизайн, вокселизатор (исследование и правила), производительность и порядок.

**Волна 2 (после влития Unity 6.3):** чистка, рендер, ядро, меню, звук, AI, инструмент вокселизатора.

Зависимости внутри волны 2:
- все ветки волны 2 начинаются от `game/develop` уже на 6.3;
- рендер переводит шейдеры и материалы сразу, а сцену VoxelSandbox — после влития чистки;
- меню делает экраны сразу; связка с загрузкой, паузой и сохранениями — по готовности ядра; содержимое магазина и ангара — по документу геймдизайна;
- звук берёт список событий из документа геймдизайна; звук на паузе замораживается через GameLoop ядра;
- AI тикает через GameLoop ядра; размер орды в дизайне — после замера;
- 3D-сцена ангара и новые эффекты делаются только на URP.

## 7. Как работают команды

### Ветки, рабочие копии, редакторы

- У каждой команды своя ветка `game/<команда>` от `game/develop` и своя рабочая копия (git worktree).
- Кому нужен Unity, открывает отдельный редактор на своей рабочей копии. Unity CLI видит все редакторы по портам (`unity-status`). Команда работает только с редактором, у которого `projectPath` — её копия.
- Чтобы не ждать полного импорта, в новую копию можно положить `Library` из основного проекта той же версии Unity.
- Основной редактор (основная папка проекта, `game/develop`) — для пользователя и тимлида: интеграция и замеры. Команда производительности снимает в нём замеры по правилам общего редактора.

### Цикл работы команды

1. Обсуждение с пользователем (в чате команды или через тимлида) → спецификация `Docs/superpowers/specs/<дата>-<тема>.md`.
2. План `Docs/superpowers/plans/<дата>-<тема>.md`.
3. Реализация силами своих субагентов.
4. Ревью кода субагентом-ревьюером и проверка агентом производительности (когда он появится).
5. Отчёт тимлиду: что сделано, ветка и коммиты, как проверить, что не проверено.
6. Пользователь смотрит результат (скриншот, видео или играет сам) и одобряет. Тимлид вливает ветку в `game/develop`, остальные команды подтягивают изменения.

### Правила для всех

- Документы на русском, код и комментарии на английском.
- Коммитить только свои пути (`git add <пути>`). Сообщение коммита заканчивается строкой `Co-Authored-By`, которую даёт системное напоминание сессии.
- Ничего не пушить на GitHub без просьбы пользователя.
- Platformer и другие проекты пользователя — только читать.
- Правила общего редактора: не делать Refresh и не перекомпилировать во время Play (проверка `EditorApplication.isPlaying` в том же вызове); не запускать тесты, пока сцена не сохранена; не сохранять чужие несохранённые сцены; если редактор в Play — спросить, прежде чем его останавливать.
- Решения, которые задевают другие команды (общие файлы, пакеты, формат данных между модулями), — через тимлида.

## 8. Риски

| Риск | Что делаем |
|---|---|
| URP меняет картинку | Влитие только после одобрения скриншотов «до и после» |
| AIKit меняется каждый день | Фиксируем коммит `5b727e9d`; переход на новую версию — отдельной задачей |
| NavMesh статичен, а воксельная земля роется | Команда AI выбирает навигацию: перестройка NavMesh по чанкам или своя навигация по вокселям |
| Неизвестен потолок числа монстров орды | Первый шаг орды — прототип и замер |
| Смерть монстра вокселизацией на лету стоит несколько мс | Для орды воксельные трупы запекаются заранее |
| Atomic — нишевый фреймворк, его документация местами врёт | Агенты работают по `Docs/AtomicGuide` |
| Много редакторов сразу: у каждой копии свой `Library` около 3 ГБ и своя память | Редактор открывают только команды, которым он нужен сейчас |
