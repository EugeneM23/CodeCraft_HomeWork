**Решения по ходу:**

- Ключ секции значений — `$vars`, а не `$values`: Newtonsoft читает `$values`, `$type`, `$id`, `$ref` как свои
  метаданные, сейв с такой секцией разбирался как испорченный. Ключи значений с `$` запрещены по той же причине.
- Компоненты Unity из скриптовых сборок (uGUI, TextMesh Pro, пакеты: имя сборки `UnityEngine*` / `Unity.*`)
  сохраняются свойствами, как компоненты движка: их состояние — за сеттерами (`Image.color` перерисовывает графику,
  поле `m_Color` — нет).
- Список «опасных» свойств (не попадают ни в All Fields, ни в Selected) собран тестом, который гоняет All Fields по
  15 частым компонентам и требует пустую консоль: так нашёлся `Collider2D.density` (предупреждение без авто-массы).
- `Library` нового worktree скопирована из `Platformer-SaveSystem`: после этого у классов `SpriteAnimator` и
  `ScreenStack` потерялась привязка MonoScript («No script asset for SpriteAnimationClip», 12 падений полного
  прогона). Переимпорт скриптов (`AssetDatabase.ImportAsset(…, ForceUpdate)` по всем `MonoScript` в `Assets/Game`)
  вылечил — это кэш, не код.

**Независимое ревью диффа** (отдельный агент) нашло 10 дефектов; каждый воспроизведён тестом и исправлен:

| # | Дефект | Исправление |
|---|---|---|
| 1 | Выключили сжатие/шифрование — старые сейвы с `#save:` читались как испорченные и уходили в `.corrupt` | `SaveLoadSystem` всегда оборачивает хранилище; выключенный шаг остаётся «читателем» (`AddReader`) |
| 2 | Вторая система «простаивала» только на словах: автосейв и сохранение при выходе писали её пустой слот поверх настоящего | Вторая система выключена (`IsIdle`): ни загрузки при старте, ни автосейва, ни сохранения при выходе |
| 3 | All Fields брал значения со ссылками внутри (`Wave[]` с префабом, `Dictionary<string, GameObject>`) — загрузка обнуляла проводку | `HoldsUnityObjects` смотрит вглубь: коллекции, словари, поля классов и структур |
| 4 | `SyncAsync` сравнивал локальный слот, снятый до запроса: сохранение во время запроса затиралось скачанным | Локальный слот читается после ответа сервера |
| 5 | `SaveActions`, указывающий на копию системы из сцены, слушал её события и после её удаления молчал | Копия (`IsIdle`) пропускается, подписка переезжает на живую систему; позже `SaveActions` убран совсем — копии сами пересылают вызовы |
| 6 | Подтверждение в меню слотов брало номер слота из строки в момент «Да»: строки переиспользуются, после обновления удалялся соседний слот | Номер слота запоминается до вопроса |
| 7 | Подсказка обещала «нельзя править», а открытый текст принимается ради старых сейвов | Честная подсказка; строгий режим `TransformSaveStorage.AcceptPlainText = false` |
| 8 | `RenameSlot` переписывал `meta.json` более новой игры, теряя её поля | Отказ (`false`), файл не трогается |
| 9 | `ExportSlot`/`CopySlot` брали битый `save.json` вместо целого `.bak` и падали | Нечитаемый файл уступает `.bak`; инспектор ловит ошибку чтения при копировании |
| 10 | `[Save]` на переопределённом свойстве давал ложную ошибку «ключ дважды» или предупреждение | Атрибут — только объявленный здесь, свойство с тем же именем берётся один раз |

## 1. Задача пользователя

> Система сохранений максимально гибкая, хорошо работает и с чистым кодом, и с компонентами. Компонент на префаб:
> указал, какие компоненты сохранять, — и он сохраняет всё, что можно; при детальной настройке — выбрать поля.
> Максимально просто, чтобы и самый неопытный сделал себе сохранения. Модуль загрузки так же казуально: кинул
> префаб в сцену — и можно управлять сохранениями: создавать слоты, удалять, настраивать, вызывать через кнопки и
> методы. Из кода — полный контроль. Удобно стыковаться с любыми сервисами и базами данных.

## 2. Что уже было и чего не хватало

| Нужно | Было (части 1–3) | Не хватало |
|---|---|---|
| Компонент на префаб, выбор компонентов | `Saveable` с флажками | Сохраняет только то, у чего есть сериализатор: свой скрипт без `[Save]` и любой чужой компонент (`Light`, компонент пака) — «нечего сохранять» |
| Выбор полей | `[Save]` в коде | Выбрать поля в инспекторе, без правки кода (чужие компоненты так не пометить) |
| Чистый C# | `GameSerializer<TService, TData>` — класс данных + наследник | Сохранить объект без своего класса-сериализатора; «положить число под ключ» |
| Кинул в сцену — работает | `SaveLoadSystem` + ассет настроек вручную | Готового префаба нет; без настроек объекты сцены молча не сохраняются; объект не переживает смену сцены |
| Слоты, кнопки | `SelectSlot`, `GetSlots`, `DeleteSlot` | Имя слота, копия, «последний слот», методы для `Button.onClick` (только `void`), события в инспекторе, меню слотов |
| Сервисы и БД | `ISaveStorage` (6 методов, `.bak`, карантин) | Простой адаптер под key-value хранилище, выбор хранилища в инспекторе, PlayerPrefs, экспорт/импорт слота одной строкой, синхронизация с сервером, сжатие и шифрование |

## 3. Решения

| Тема | Решение |
|---|---|
| Режим компонента | У каждого компонента в `Saveable` — режим: **Auto** (как раньше: свой сериализатор → встроенный → `[Save]`), **All Fields** (всё, что можно), **Selected** (только отмеченные в инспекторе поля и свойства) |
| Что по умолчанию | Как раньше: отмечено всё, у чего есть сериализатор. Компонент без сериализатора по умолчанию не отмечен — отметка включает All Fields. Иначе префаб игрока начал бы сохранять настройки всех механик |
| All Fields у своего скрипта | Поля, которые сериализует Unity (`public`, `[SerializeField]`), авто-свойства и `[Save]`. Ссылки на Unity-объекты — с версии 0.4.0 берём, но только те, что сейв может выразить; остальное не пишем, и загрузка проводку не обнуляет (раздел 9). До 0.4.0 ссылки не брались совсем |
| All Fields у компонента движка | Публичные свойства с `get` и `set` значимых типов (числа, `bool`, строки, перечисления, `Vector*`, `Color`…), без устаревших и опасных (`material`, `mesh` создают копии) |
| Selected | Любое поле экземпляра (и приватное несериализуемое состояние вроде `_timer`) и публичное свойство с `get`/`set`, ссылки на Unity-объекты — можно (по правилам ссылок части 3) |
| Загрузка выбранных членов | Поштучно: член, который не прочитался или не записался, — предупреждение, остальные применяются (лучшее усилие для чужих компонентов). `[Save]`-поля по-прежнему «всё или ничего» |
| `[Save]` | Теперь и на свойствах |
| Чистый C# | Три пути по возрастанию контроля: **значения** `Values.Set("coins", 5)` (секция `$vars` слота); **объект целиком** `Register("stats", stats)` — `[Save]`-члены, а без них все публичные поля и свойства; **геттер/сеттер** `Register("coins", () => coins, v => coins = v)`; дальше — `GameSerializer` как раньше |
| Доступ из кода | `ISaveLoadService` (как раньше, через `ServiceLocator` в нашей игре) и `SaveLoadSystem.Current` — статическая ссылка на активную систему для проектов без локатора и для кнопок |
| Слоты | Номер слота, как раньше; в `meta.json` добавились имя слота, время создания, сцена. Методы: `HasSlot`, `GetSlot`, `RenameSlot`, `CopySlot`, `GetLatestSlot`, `GetFreeSlot`, `ExportSlot`/`ImportSlot`. Старые `meta.json` читаются (новые поля пустые) |
| Кнопки | У `SaveLoadSystem` — `void`-методы для `Button.onClick` (`SaveGame`, `LoadGame`, `SaveToSlot(int)`, `LoadFromSlot(int)`, `DeleteSlot(int)`, `NewGame`, `ContinueGame`, `RenameCurrentSlot(string)`) и `UnityEvent` (`Saved`, `Loaded`, `SlotsChanged`). Кнопки вешаются прямо на `SaveSystem` своей сцены: копия префаба (следующая сцена, сцена после загрузки) не удаляет себя, а пересылает вызовы и события живой системе (`IsIdle`). Был компонент `SaveActions` для этого — убран 24.10 как лишний |
| «Кинул префаб — работает» | Префаб `SaveSystem` в модуле (`Prefabs/`): `SaveLoadSystem`, переживает смену сцены (корневой объект — `DontDestroyOnLoad`, копии в других сценах — пересылки). Флажок «Save Scene Objects»: редактор сам находит или создаёт ассет `SaveSystemSettings` и подставляет его. Меню *GameObject → Save System* создаёт систему и меню слотов в сцене |
| Меню слотов | Сборка `SaveSystem.UI` (uGUI + TextMeshPro): `SaveSlotsMenu` — список слотов (имя, дата, время игры, сцена), режимы «сохранить» / «загрузить», удаление и переименование с подтверждением; префаб `SaveSlotsMenu`. Ни о паузе, ни о `ScreenStack` модуль не знает |
| Хранилище в инспекторе | `SaveLoadSystem`: «Files» (как раньше, папка), «PlayerPrefs» (веб, простые проекты), «Custom» — ассет-наследник `SaveStorageAsset` (своя БД). Из кода — `UseStorage(ISaveStorage)` как раньше |
| Адаптер под БД | `KeyValueSaveStorage`: три метода (`TryGet`, `Set`, `Remove`) по строковому ключу — вся семантика слотов, `.bak` и карантина в базе; `PlayerPrefsSaveStorage` — его наследник |
| Сервер / облако | Локальное хранилище остаётся главным, удалённое — зеркало: `IRemoteSaveStorage` (4 асинхронных метода: список, скачать, загрузить, удалить пакет слота) и `SaveSync` (`PushAsync`, `PullAsync`, `SyncAsync` — новее побеждает, выгрузка после каждого сохранения по флажку). Пакет слота — одна JSON-строка (`ExportSlot`) |
| Сжатие, шифрование | По желанию, декоратор хранилища `TransformSaveStorage` со ступенями `GZipSaveTransform`, `AesSaveTransform` (AES-CBC + HMAC — от правки сейва руками и любопытных глаз, не защита от взлома: ключ в сборке). Старый открытый JSON читается и при включённых ступенях. По умолчанию — открытый JSON |
| Формат | `save.json` не меняется (`formatVersion` 1). Данные компонента в режимах All Fields / Selected — объект «имя члена → значение», версия 1 |

## 4. Устройство

```
код игры / кнопки ──► SaveLoadSystem (Current, void-методы, UnityEvent) ◄── копии SaveSystem в других сценах,
                          │                                                 SaveSlotsMenu (uGUI)
                          ▼
                    SaveLoadService ──► Values ($vars)
                          │   ├── IGameSerializer: GameSerializer, ObjectSerializer, DelegateSerializer
                          │   └── слой объектов: Saveable → режим компонента → сериализатор:
                          │          Auto (свой / встроенный / [Save]) | All Fields | Selected → MembersSerializer
                          ▼
                    ISaveStorage ◄── FileSaveStorage | PlayerPrefsSaveStorage (KeyValueSaveStorage) | SaveStorageAsset
                          │              └── TransformSaveStorage (GZip, AES) — по желанию
                          └── ExportSlot / ImportSlot ◄──► SaveSync ◄──► IRemoteSaveStorage (сервер, БД, облако)
```

## 5. API

### 5.1. Значения слота (core)

```csharp
ISaveLoadService saves = SaveLoadSystem.Current;
saves.Values.Set("coins", 120);
int coins = saves.Values.Get("coins", 0);        // default when missing or unreadable
saves.Values.Has("door_open"); saves.Values.Delete("door_open");
```

Значения живут в слоте: `SelectSlot` (новая игра) очищает их, `Load` заменяет сохранёнными (секции нет — пусто).
Типы — всё, что пишет `SaveJson` (примитивы, строки, перечисления, Unity-структуры, списки, словари, классы).
Ссылок на Unity-объекты в значениях нет.

### 5.2. Объект и геттер/сеттер

```csharp
saves.Register("stats", playerStats);                    // ObjectSerializer: [Save] members or all public ones
saves.Register("volume", () => volume, v => volume = v); // DelegateSerializer<T>
saves.Unregister("stats");
```

`ObjectSerializer` (сборка `SaveSystem.Objects` — ему нужны ссылки на ассеты) пишет члены объекта и при загрузке
заполняет **тот же** объект. Члены: `[Save]`, а если их нет — публичные поля, `[SerializeField]`-поля и публичные
свойства с `get`/`set` (у Unity-объекта — только поля по правилам Unity); ссылки на Unity-объекты — только помеченные
`[Save]`. Годится и для `ScriptableObject`.

### 5.3. Режимы компонентов `Saveable`

```csharp
saveable.SetMode("Light", SaveMode.AllFields);
saveable.SetMembers("Visual/LineRenderer", "startWidth", "endWidth"); // SaveMode.Selected
saveable.SetSaved("Rigidbody2D", false);
```

Инспектор: все компоненты объекта и детей с флажком; у отмеченного — выпадающий режим; у Selected — список членов с
флажками. Ключи компонентов — как в части 3.

### 5.4. Слоты

```csharp
SlotInfo info = saves.GetSlot(2);             // null when empty; Name, SavedAtUtc, CreatedAtUtc, Scene, PlayTime, Summary
saves.RenameSlot(2, "Before the boss");
saves.CopySlot(2, 5);
int latest = saves.GetLatestSlot();           // -1 when there are no saves
int free = saves.GetFreeSlot();               // first slot without data
string package = saves.ExportSlot(2);         // one JSON string: every file of the slot
saves.ImportSlot(7, package);
```

`SaveLoadSystem`: `SaveToSlot(n)` — «сохранить как» (снимок остаётся), `LoadFromSlot(n)` — выбрать и загрузить,
`NewGame()` — первый свободный слот (или текущий, если флажок «один слот»), пустой снимок, стартовая сцена
(поле; пусто — перезагрузить активную), `ContinueGame()` — последний слот, нет сохранений — `NewGame()`.

### 5.5. Хранилища и сервисы

```csharp
public sealed class MyDbStorage : KeyValueSaveStorage
{
    protected override bool TryGet(string key, out string text) { ... }
    protected override void Set(string key, string text) { ... }
    protected override void Remove(string key) { ... }
}

public sealed class MyServer : IRemoteSaveStorage
{
    public Task<IReadOnlyList<int>> ListAsync(CancellationToken token) { ... }
    public Task<string> DownloadAsync(int slot, CancellationToken token) { ... }   // null: nothing there
    public Task UploadAsync(int slot, string package, CancellationToken token) { ... }
    public Task DeleteAsync(int slot, CancellationToken token) { ... }
}

var sync = new SaveSync(saves, new MyServer()) { UploadAfterSave = true };
SyncOutcome outcome = await sync.SyncAsync(slot);  // the newer side wins: Uploaded, Downloaded, UpToDate, Failed
```

В инспекторе: `SaveStorageAsset` (свой ассет — `CreateStorage()`) и `RemoteSaveStorageAsset` (`CreateRemote()`),
флажки «Compress», «Encrypt» + ключ.

## 6. Совместимость

- Формат `save.json` и данные встроенных сериализаторов не меняются; старые сейвы читаются.
- `meta.json` получает новые поля; старый — без них (имя пустое, время создания = время сохранения).
- Сериализованные данные `Saveable` (`_excluded`, `_options`) не меняются, режимы — новое поле `_rules`.
- `ISaveLoadService` расширяется — фейк в тестах игры дополняется.
- Наша игра: `[Services]` и `SaveDebugHotkeys` работают как раньше; `SaveLoadSystem` — ребёнок `[Services]`, сам в
  `DontDestroyOnLoad` не переносится (только корневой объект).

## 8. Отложено

- Миниатюры слотов (скриншот) — структура `meta.json` к этому готова.
- HTTP-клиент `IRemoteSaveStorage` из коробки — в README пример на `UnityWebRequest`.
- Меню слотов внутри `GameUI` нашей игры (через `ScreenStack`) — отдельной задачей игры.
- IL2CPP: режимы All Fields / Selected и `ObjectSerializer` работают рефлексией по членам — при сильной обрезке кода
  (Managed Stripping Level выше Minimal) нужен `link.xml` для сохраняемых типов; вместе с `link.xml` для Newtonsoft
  перед первой IL2CPP-сборкой.

## 10. Версия 0.5.0: вся сцена одним компонентом, `Saveable` — явный список (10.11.2026)

### 10.1. Требования

1. **Ленивый путь.** Бросил один компонент в сцену — состояние сцены сохраняется, на объекты ничего вешать не
   нужно. Охват — как можно шире, работоспособность — гарантированная.
2. **Точный путь.** `Saveable` на объектах: сохраняются только они, и только то, что на них отмечено.
3. **Проверка без кода и без отдельного компонента**: сохранить и загрузить кнопкой в инспекторе, клавишей, методом.
4. **Не плодить компоненты.** В рантайме их по-прежнему два: система и `Saveable`.
5. `Saveable` писал слишком много (всё, у чего есть сериализатор, со всеми детьми: у игрока FPS Microgame — 102
   `Transform`, 23 `ParticleSystem`) — должен стать списком выбранных компонентов.

### 10.2. Решения

| Тема | Решение | Почему так |
|---|---|---|
| Сколько компонентов | Два. Режим сцены, клавиши и «проверка» — в самом `SaveLoadSystem` (в меню — Save System) | Отдельный «тестовый» компонент — ещё одна вещь, в которой пользователь теряется |
| Режим сцены | `SaveScope`: `WholeScene` или `Saveables` (поле `_scope`, принадлежит сцене компонента). Добавленный руками компонент — `WholeScene` с клавишами; префаб `SaveSystem`, автосистема и компоненты из старых сцен — `Saveables` | Старые сцены и игры не меняют поведение; ленивый путь — одно действие |
| Как узнавать объекты без `Saveable` | Список «объект → ID» в самом компоненте, хранится в файле сцены; ведёт редактор (`SaveSceneBaker`: сохранение сцены, вход в Play, сборка, добавление компонента) | Скрытые `Saveable` в сцене — сотни компонентов и переопределений префабов; путь в иерархии — сейвы ломаются от переименования. `GlobalObjectId` проверен и отброшен: в Play у экземпляров префабов он другой |
| ID | 12 hex, FNV-1a от пути объекта в иерархии (двойники — с номером); попав в список, ID не меняется | Одна сцена → одни ID на любой машине и в сборке, даже если список не был сохранён; переименование после этого сейвы не ломает |
| Кто в списке | Все объекты сцены, кроме объекта системы, объектов с `Saveable` и всего под ними, `Static` (по галочке), `Ignored`, `EditorOnly` | Статичная геометрия — тысячи объектов без состояния (FPS Microgame: 4458 объектов, из них 3963 статичных) |
| В рантайме | При загрузке сцены каждому объекту списка добавляется скрытый `Saveable` (`Saveable.Adopt`, `HideInInspector`, в файл сцены не попадает) с ID из списка и общей политикой `SavePolicy` | Реестр, ссылки, «уничтожен — остаётся уничтоженным», фазы загрузки и `Start` после чужих `Start` работают без второй подсистемы |
| Что брать с объекта | `SaveCoverage`: `Transforms`, `Physics`, `Scripts`, `Effects` (флаги в инспекторе). Скрипт — свой сериализатор → `[Save]` → All Fields со ссылками. Рендереры, свет, камеры, UI — нет | Состояние игры, а не вид |
| Размер | `Transform` пишется, только если объект сдвинулся относительно состояния сцены (снимок берётся в `Awake` системы, порядок −9000, до скриптов сцены); объекты под `Animator` — никогда; коллайдер — только если его включили или выключили; объект без единой записи в сейв не попадает; объект сцены отвечает только за себя (дети — отдельные объекты) | Замер на MainScene FPS Microgame: первый вариант без этих правил — 524 КБ и 138 мс (статичные дети динамического родителя с `MeshCollider` — 96 КБ, флаги детей — 61 КБ); с правилами — 84 КБ, 42 объекта, 18 мс |
| Снимок только для `Transform` | Скрипты, тела и эффекты пишутся всегда | Значение, которое скрипт случайно выбрал в `Awake` и больше не менял, при сравнении со снимком «после `Awake`» не попало бы в сейв и после загрузки стало бы другим. Снимок `Transform` берётся до `Awake` скриптов — у него этой дыры нет |
| Созданное в игре | Перед сохранением ищутся объекты, которых не было в сцене; объект с состоянием (скрипт игры или тело) сохраняется как копия префаба, в честь которого назван (`X(Clone)` → `X`). Префабы — те, от которых зависит сцена, и из `Resources` (список в компоненте) | В сборке Unity не знает, из какого префаба объект. По имени — самый широкий охват без разметки; зависимости сцены и `Resources` и так в сборке, размер не растёт. Эффекты без скриптов не сохраняются: у возвращённого объекта нет таймера `Destroy(obj, t)`, он жил бы вечно |
| То, что игра создаёт сама при старте | Сохранённые копии «по имени» ждут первого `Start` любого `Saveable` (порядок 32000 — после всех `Start` сцены) и занимают объект с тем же именем под тем же родителем; только если такого нет — создаются | Иначе оружие, выданное в `Start`, и объекты пула удваивались бы при каждой загрузке |
| Система на объекте сцены | Компонент на корневом объекте с детьми или другими компонентами, или на ребёнке объекта, который игра не держит в `DontDestroyOnLoad`, создаёт `SaveSystem (live)` с теми же настройками (`JsonUtility`) и остаётся копией-пересылкой. Ребёнок удерживаемого корня (`[Services]`) и «чистый» объект — как раньше | Раньше корневой объект уезжал в `DontDestroyOnLoad` целиком: уровень с геометрией удваивался после первой же загрузки. «Бросить на что угодно» должно работать |
| `Saveable` | Явный список: `_explicit` + `_included`. Добавленный в редакторе стартует со списком «`Transform`, тело и свои скрипты объекта» (`UseExplicitList`). Старые (`_explicit = false`) — как раньше, с кнопкой и пунктом меню «перейти на список» | Старые сцены и префабы не меняют сейвы молча; новые не разрастаются |
| Клавиши | `SaveHotkey` F1…F12, по умолчанию F5 / F9; работает и с Input System (ссылка в asmdef, `SAVE_INPUT_SYSTEM`), и со старым Input | Функциональные клавиши одинаково называются в обоих API |
| Сводка | `SaveLoadSystem.LastSave` (`SaveReport`): исход, слот, объектов, знаков, мс и всё, что модуль написал в консоль во время сохранения | «Что не сохранилось и почему» — в инспекторе, а не в консоли среди прочего |

### 10.3. Что проверено и что нет

Проект-проба — FPS Microgame (URP, Input System). Тесты модуля в его редакторе: EditMode 400/400, PlayMode
136/136 (`WholeSceneTests` — 11, `SaveableListTests` — 5, `SaveSceneBakerTests` — 12). Тесты самой игры-пробы
(`FpsSaveTests`, 7): игрок, враг с целью, убитая турель, пули с владельцем, взятая и сдвинутая аптечки уровня без
`Saveable`, выданное в `Start` оружие не удваивается за две загрузки, сейв всей сцены — 84 КБ без предупреждений.

Не проверено: сборка игрока (список печётся в `IProcessSceneWithReport`, но сборку не делали); несколько сцен с
режимом «вся сцена» одновременно (additive); проекты на старом Input; в самом Platformer модуль этой версии не
компилировался.

### 10.4. Чего режим не умеет

- Приватное состояние скрипта (поле без `[SerializeField]`) в All Fields не входит: `Saveable` + Selected или `[Save]`.
- Смена родителя у объекта сцены не сохраняется.
- Объект, который игра создаёт позже первого кадра, после загрузки удвоится (сохранённая копия уже создана).
- Списки игры, в которых она держит созданные объекты (слоты оружия), заполняет код игры: подобранное оружие
  вернётся как объект (если сцена знает его префаб), но не как слот.
- Объект, созданный в игре из префаба, от которого сцена не зависит (подгружен по адресу), не узнаётся — предупреждение.

### 11.2. Моменты времени (правки 5 и 6)

`Time.time` начинается с нуля при каждом запуске игры, а между сохранением и загрузкой в одном запуске успевает уйти
вперёд. Приватное `m_LastTimeShot = Time.time`, записанное как число, после загрузки врёт в обоих случаях: в новом
запуске оно в будущем (оружие молчит, пока часы не дойдут), в том же — «с выстрела» прошло больше, чем было. А не
записанное совсем (первый вариант правки 5) даёт «выстрела не было»: оружие сразу перезаряжается. В FPS Microgame
таких полей больше десятка (`m_LastTimeShot`, `m_LastTimeDamaged`, `m_TimeStartedDetection`…).

Решение: член, который Unity не сериализует (приватное поле, авто-свойство) у скрипта, типа `float`/`double`, с
`time` в имени и без слов-длительностей (`timer`, `timeout`, `lifetime`, `playtime`, `elapsed`, `total`, `remain`,
`left`, `delta`, `accum`, `duration`, `cooldown`, `interval`, `delay`, `scale`, `step`, `played`, `spent`) —
**момент** (`SaveMember.IsMoment`). Он пишется под ключом `<имя>@ago` как «секунд назад» (`Time.timeAsDouble −
значение`; `-Infinity` — `"never"`, `+Infinity` — `"not yet"`) и возвращается как `Time.timeAsDouble − секунд назад`
в момент загрузки. Сейв, записанный до этого, держит значение под обычным ключом — оно читается как раньше.
Работает в *All Fields*, *Selected* и в режиме сцены; `[Save]` (`FieldsSerializer`) пишет как есть — там ключи
задаёт автор. Публичные и `[SerializeField]`-поля — всегда как есть (`MaxLifeTime` — настройка).

Правило по имени грубое в обе стороны: момент с другим именем (`_firedAt`) запишется числом, длительность с `time`
в имени без слова из списка (`_chargeTime`) будет сдвинута. Часы — только `Time.time`: момент, взятый из
`Time.unscaledTime` или `realtimeSinceStartup`, сдвинется на разницу игровых часов.

### 11.3. Следствие правок 2 и 6

В сцене с режимом «вся сцена» список `Saveable` только добавляет: снятая галочка больше не значит «не сохранять» для
скриптов, тел и эффектов, а *Selected* — «только эти поля». Убрать компонент из сейва — галочкой вида в *Take From
Objects* или режимом *Scope = Saveables*. В сценах с *Scope = Saveables* и у объектов в `DontDestroyOnLoad` список
работает как раньше. Инспектор `Saveable` об этом пока не сообщает — отложено. Сейв `MainScene` FPS Microgame вырос
с 84 до 101 КБ (47 объектов, 13 мс).

## 12. Версия 0.6.0: проба на игре с Zenject и пулами (10.11.2026)

Проба — SPrototype (Unity 6000.0.38f1): Zenject (`ProjectContext`, `SceneContext`, `GameObjectContext` у каждой
сущности), всё живое создаётся через пулы игры (`GameFactory`), уровень — две сцены (уровень и системная, вторая

### 12.2. Чего это не решает

- **Состояние всего контейнера подряд сохранять нельзя.** Проба: в сейв попали флаги и таймеры машины состояний
  врага (`_isBusy`, таймеры решений), после загрузки враг застыл — сама машина состояний в сейв не входит. Связка
  игры отдаёт только классы с `[Save]`; модуль умеет оба варианта, выбор за игрой.
- **Live Load не спасает, когда нужна перезагрузка сцены** (см. правку 6): игра с пулами в `ProjectContext` тогда
  ломается, как и раньше. Чинится в игре — пулы должны переживать смену сцены или пересоздаваться.
- **Правило 10 — по имени**: флаг настройки с другим названием (`_ready`) под него не попадёт.
- **Список сторонних сборок** не видит код из Asset Store, который лежит в `Assets` вне папок `Plugins` и собирается
  в `Assembly-CSharp`: он считается кодом игры (от этого правка 10).
- **Сериализуемые флаги сохраняются как есть.** В пробе пауза — `[SerializeField] bool` в ядре каждого персонажа:
  сохранённая на паузе игра после загрузки стоит, пока паузу не снять.
- **Аддитивная сцена, которую игра грузит сама позже первого кадра** (после затемнения, по цепочке `await`), к этому
  моменту уже загружена модулем — получится две копии.
- **Оружие, подобранное после сохранения**, Live Load не убирает: чьё оно, знает только игра, а её инвентарь в сейв
  не входит.

### 12.3. Что проверено и что нет

SPrototype, редактор 6000.0.38f1: EditMode 428/428, PlayMode модуля 155/155. В запущенной игре: старт без ошибок с
системой в обеих сценах; «продолжить» (сохранить, выйти из Play, войти снова) — игрок и враги на сохранённых местах,
без дублей; загрузка в игре одним скриптом в одном кадре — игрок, враг и здоровье вернулись, враг, заспавненный после
сохранения, ушёл в пул, сцены не перезагружались; толпа из 8 и из 18 врагов из циклического спавнера — все на местах
со своим здоровьем; ракеты в замедленном времени — после загрузки остались 5 сохранённых с тем же прогрессом

## 13. Версия 0.7.0: не посреди начатого, данные с первого кадра (11.11.2026)

Проба — домашка MVx (`CodeCraft_HomeWork`, ветка `HomeWork_05_MVx_patterns`, Unity 6000.5.6): Zenject, всё
состояние — в обычных классах (деньги, планеты), вьюхи на uGUI и DOTween. Модуль стоит пакетом из ветки
`module/SaveSystem`, связка игры — сборка `Game.Saves` (сериализаторы денег и планет, регистрация при сборке
контейнера). По жалобе пользователя: монетка дохода, летящая к банку, не сохранялась.

### 13.1. Что нашли и что сделано

| № | Что было | Причина | Что сделано |
|---|---|---|---|
| 1 | После загрузки монетка дохода спрятана, хотя доход готов | Вьюха планет читает состояние в `OnEnable`, пока сцена просыпается, а *Load On Start* грузил слот в `Start` системы — позже. Планета загружена верно, вьюха уже показала старое | Раннее чтение: при *Load On Start* слот читается в момент, когда к системе впервые обращаются до её `Start` (`SaveLoadService.Preload` из `CreateService`). Только чтение файла в снимок: зарегистрированные и все, кто зарегистрируется дальше, сразу получают данные (`ApplyOnRegister`). Ничего не пишется, не переносится в `.corrupt`, событий нет — битый или новый файл разбирает полная загрузка в `Start`. Если до `Start` к системе никто не обращается, всё как раньше: `UseStorage` и `Configure` по-прежнему можно звать до старта (на это опираются тесты демо-сцен и README) |
| 2 | Сохранение в полёте монетки записывало «доход готов, денег нет» | Деньги начисляются в `OnComplete` твина DOTween; колбэк — код, в сейв он не попадает | «Начатое» (`IWorkInFlight`: `IsBusy`, `Finish`, `Drop`; по умолчанию `DOTweenWork` — DOTween через reflection, без ссылки на сборку): твины, которые играют, имеют `OnComplete` и не зациклены навсегда. Сохранения, которые система делает сама (автосейв, F5, `SaveGame`, `SaveToSlot`, потеря фокуса), ждут конца начатого (`MAX_WAIT_FOR_WORK` = 5 с реального времени, потом сохраняют всё равно; несколько запросов — одно сохранение, `IsSaveWaiting`); выход и пауза приложения сначала доигрывают его с колбэками (`Finish`); `Load` обрывает его без колбэков (`Drop`) и отменяет ожидающее сохранение — награда, начатая после сохранения, не падает в загруженную игру. `Save()` из кода не ждёт никогда. Галочка *Finish Work Before Save* (`FinishWorkBeforeSave`, по умолчанию включена); `SaveLoadSystem.WorkInFlight` — своя реализация или `null` |
| 3 | Пользователь ждал от загрузки ровно момент нажатия «сохранить» — монетку в воздухе, которая долетит и заплатит; правка 2 давала уже долетевшую | Вернуть полёт может только игра: «что сделать по прилёту» — её код | Твин с id `SaveLoadSystem.WORK_SAVED_BY_GAME` (DOTween `SetId`; читается и `stringId`, и `id`) — полёт, который игра сохраняет сама: сохранение его не ждёт и выход его не доигрывает, загрузка всё равно обрывает. В MVx `CoinMoveController` запускает полёт с этой меткой, пишет `[Save]` откуда и сколько пролетел (`ISaveCallbacks.OnBeforeSave`), после загрузки запускает заново и перематывает (`Goto`); на монетках — `Saveable` с одним этим скриптом. Пример — в README |

### 13.2. Что проверено и что нет

SPrototype, редактор 6000.0.38, batchmode: EditMode 428/428, PlayMode модуля 167/167 (новые: `WorkInFlightTests` 9 —
кнопка и автосейв ждут, `Save()` не ждёт, выход и пауза доигрывают, загрузка обрывает и отменяет ожидающее
сохранение, выключенная галочка, предел ожидания; `LoadOnStartEarlyTests` 3 — регистрация до `Start` получает данные
сразу, без *Load On Start* — нет, битый файл при раннем чтении молчит). В MVx (редактор 6000.5.6, время замедлено,
чтобы полёт длился несколько секунд): F5 в полёте сохраняет сразу, после F9 монетка снова в воздухе с того же места
и долетает — одно начисление; выход из Play в полёте — следующий запуск продолжает полёт; монетка видна с первого
кадра после старта и после F9; F9 без метки (правка 2) — лишнего начисления нет. До правки 3 проверены также
автосейв/F5, дожидающиеся монетки, и выход, доигрывающий её.

Не проверено: пропуск твина с меткой — только в игре (в тестовых проектах модуля DOTween нет); сборка игрока
(IL2CPP с вырезанием кода может убрать методы DOTween, которые игра сама не зовёт, — тогда система молча сохраняет
как раньше); в самом Platformer модуль этой версии не компилировался — у игры есть DOTween, поэтому её автосейв
теперь ждёт её твины с колбэками, а выход их доигрывает.

Наблюдение из пробы: проверять в редакторе, где одновременно играет человек, нельзя — его F5/F9 и клики
перемешивают показания (так в одном из прогонов «лишние» 545 монет и самопроизвольная перезагрузка сцены).
