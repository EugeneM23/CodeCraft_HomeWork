# BallArena — минимальная сетевая сцена на Photon Fusion 2

Дата: 2026-11-01. Статус: согласовано, в реализации.

## Цель

Две капсулы в коробке катят физический мяч в ворота соперника. Собрать
standalone-билд для Windows и сыграть с другом через интернет без проброса
портов, VPN и выделенного сервера.

Это тренировочная сцена по гайду из этой папки, а не заготовка под продакшн.

### Поправка по ходу работы: SDK остался 2.0.5

Планировалось взять Fusion 2.1.3. Скачать его автоматически не удалось:
`downloads.photonengine.com` без залогиненного аккаунта Photon отдаёт не пакет,
а редирект на главную страницу. Чтобы не отдавать непроверенный код, проект
собран на Fusion 2.0.5 из учебной раздачи (`03 - Кинематика и физика объектов`),
скопированы только `Fusion`, `FusionAddons`, `PhotonLibs` — без демок и меню.
Это дало полноценную компиляцию и рабочий билд. Шаги перехода на 2.1.3 описаны
в `BallArena/README.md`; версия Unity при этом остаётся выбранной 6000.0.38f1.

Побочный плюс: гайд выведен ровно из 2.0.5, так что расхождения версий нет вовсе.

### Итог

Собрано и проверено на Fusion **2.1.3** + Unity **6000.0.38f1**. Два экземпляра
билда играют через Photon Cloud: роли, спавн обоих игроков, репликация мяча,
зачёт гола, счёт на клиенте, сброс раунда — работают, исключений нет.

Путь к этому занял четыре отдельных бага; все четыре — про SDK, ни один про
игровую логику. Разбор каждого ниже.

### Баг 1: Fusion 2.0.5 несовместим с Unity 6

Выяснено тестом на двух сборках с реальным App ID. Подключение, роли хост/клиент,
репликация объекта игрока — работают. Но **каждое** обращение к `[Networked]`
падает в рантайме:

```
FieldAccessException: Field `Fusion.NetworkBehaviour:Ptr' is inaccessible
  from method `BallArena.MatchManager:set_ScoreLeft (int)'
```

За 24 секунды — 692 исключения на хосте и больше на клиенте.

Разбор причины:

1. Поле `Fusion.NetworkBehaviour.Ptr` — **internal**. Проверено компиляцией
   пробника: обращение к нему из `Assembly-CSharp` даёт `CS1061`.
2. Internals `Fusion.Runtime` выданы только `Fusion.CodeGen` и
   `Fusion.Unity.Editor` — проверено по строкам DLL. Пользовательской сборке — нет.
3. Ткач Fusion (`ILPostProcessor` в `Fusion.CodeGen`) переписывает каждое
   `[Networked]`-свойство в **прямое обращение к этому internal-полю** из
   пользовательской сборки. Технически это невалидный IL: он работает только там,
   где рантайм не проверяет доступ к полям.
4. Mono в Unity 2022.3, под которую писан SDK, эту проверку не делает — поэтому весь
   учебный курс работает. Mono в Unity 6 проверку делает.
5. SDK не повреждён при копировании: `Fusion.Runtime.dll` побайтово совпадает с
   учебной раздачей (`cmp`).

Это же объясняет, почему страница загрузки Photon заявляет Unity `6.0.x` только для
текущих сборок (2.0.11+ и 2.1.x), а 2.0.5 от февраля 2025 в этот список не попадает.

Пробовал обойти штатным механизмом Mono/CoreCLR — объявил в своей сборке
`[assembly: IgnoresAccessChecksTo("Fusion.Runtime")]`. Атрибут попал в собранную
`Assembly-CSharp.dll` (проверено), но Mono в Unity 6 его **не уважает**: 692
`FieldAccessException` остались на месте. Обход удалён как мёртвый код.

**Решение:** пользователь скачал Fusion 2.1.3. В нём `Ptr` стал публичным
документированным полем (`F:Fusion.NetworkBehaviour.Ptr` в XML-доках), и все
`FieldAccessException` исчезли.

### Баг 2: аддон физики вынесен из пакета

Fusion 2.1 не содержит `FusionAddons/Physics` — аддоны стали отдельными
загрузками, и `fusion-physics-for-fusion-2.1.x-2.1.3.unitypackage` тоже за
логином. Исходники аддона от 2.0.5 собираются против 2.1.3 без единой ошибки и
работают — проверено запуском. Пока оставлены они.

### Баг 3: `[Rpc]` падает с MethodAccessException

Ткач вставляет в каждый RPC вызов `NetworkBehaviourUtils.CheckInvokeRpc`, а этот
метод для пользовательской сборки закрыт. Проверено дважды: рантайм-исключением и
компиляцией пробника (`CS0117`). То есть ровно та же болезнь, что в баге 1, но
для RPC она в 2.1.3 не вылечена.

**Решение:** RPC не нужен. Ник уезжает на хост в `StartGameArgs.ConnectionToken`,
хост читает его через `Runner.GetPlayerConnectionToken(player)` в
`OnPlayerJoined` и пишет в `[Networked]` внутри `onBeforeSpawned`. Это механизм
гл. 09, и он даже лучше RPC: ник известен до первой репликации, без round-trip.

### Баг 4: сценовые `NetworkObject` не регистрируются

`MatchManager` лежал в сцене на `[Match]` с `NetworkObject`. Префаб запекался,
`NetworkedBehaviours` заполнялся, `Flags` обновлялись — но в рантайме объект
навсегда оставался `NetworkTypeId = None`, `IsValid = false`, и `Spawned()` не
вызывался. Ни одной ошибки в логе. Рядом заспавненный префаб игрока в тот же
момент имел `typeId = [Prefab 1]`, `IsValid = true`.

Проверено периодическим дампом всех `NetworkObject` каждые 3 секунды: состояние
`[Match]` не менялось за всё время сессии. Передача сцены через
`NetworkSceneInfo.AddSceneRef` вместо неявного приведения `SceneRef` ничего не
изменила (но оставлена — это документированный способ).

**Решение:** `MatchManager` переехал на префаб `Match.prefab`, который хост
спавнит при входе первого игрока. Префаб не может ссылаться на объекты сцены,
поэтому точки и зоны он находит через сценовый маркер `ArenaMarkers` —
тот же приём, что `WorldTransform` в гл. 03. Счёт доезжает до UI через
статическое событие, потому что UI в сцене не может сослаться на объект,
которого при загрузке сцены ещё нет.

### Расхождение с гайдом, найденное в коде SDK

Пункт 23 чеклиста гл. 03 требует расставить `[OrderBefore]` / `[OrderAfter]`
между симуляцией физики и своими запросами. **Таких атрибутов в Fusion 2.0.5 не
существует** — проверено по `Fusion.Runtime.dll` и по XML-докам: это API Fusion 1.
Ближайшее, что есть, — `[SimulationBehaviour(Stages =, Modes =, Topologies =)]`,
и оно ограничивает, где компонент исполняется, а не в каком порядке.

По §7 CLAUDE.md прав здесь исходник, а не глава. Следствие для этой сцены:
порядок «выставить скорость до `Physics.Simulate` этого тика» задать нечем,
цена — максимум один тик задержки, одинаковый на всех пирах, детерминизм цел.
Главу 03 стоит поправить.

Подписи остального API сверены по главе 90 и по реальному SDK, не по памяти.

## Границы

Чего в сцене сознательно нет: лобби и матчмейкинга, реконнекта, host migration,
лаг-компенсации, Interest Management, пулинга, звука, анимации, меню настроек,
Shared Mode, WebGL. Всё это — отдельные главы гайда, и ни одно из них не нужно,
чтобы двое играли в мяч.

## Топология

Host Mode, `GameMode.AutoHostOrClient`. Первый, кто вошёл с данным кодом комнаты,
становится хостом и считает всю истину: позиции капсул, физику мяча, счёт.
Второй — клиент: отправляет намерение (`INetworkInput`), предсказывает, получает
состояние обратно. Это главное правило гайда (ядро, строки 401–485), и ни один
скрипт его не нарушает: ни одной записи `[Networked]` вне `HasStateAuthority`.

Трафик идёт через релей Photon Cloud. Отсюда и берётся «просто через интернет»:
оба пира — исходящие TCP/UDP-соединения к облаку, входящих портов не нужно.

## Физика

Физику у Unity отбирает Fusion — иначе Rigidbody не детерминирован и
ресимуляция разъедется (гл. 03, шаг 1).

На объекте раннера лежит `RunnerSimulatePhysics3D`:

```
PhysicsAuthority        = Fusion
PhysicsTiming           = FixedUpdateNetwork
ClientPhysicsSimulation = SimulateAlways
DeltaTimeMultiplier     = 1
SetUnityFixedTimestep   = false
```

Компонент ставится **руками**. Если его не положить, `NetworkRigidbody`
добавит свой с `ClientPhysicsSimulation = Disabled`, и клиентское предсказание
физики умрёт молча.

И мяч, и капсулы — динамические `Rigidbody` с `NetworkRigidbody3D` и **без**
`NetworkTransform` (`NetworkRigidbodyBase : NetworkTRSP` сам носитель
TRSP-состояния). Оба в `Spawned()` вызывают `Runner.SetIsSimulated(Object, true)` —
это парная настройка к `SimulateAlways`, без неё прокси форсятся в
`isKinematic = true` и дёргаются.

`InterpolationTarget` у обоих — **дочерний** `Visual`, не корень. Корень держит
коллайдер и Rigidbody и обязан стоять в тиковой позиции.

Капсула — не кинематическая намеренно: кинематический `transform.position +=`
не толкает динамический мяч как надо. Капсулой двигаем через `linearVelocity`
в `FixedUpdateNetwork`, и мяч получает честный физический удар.

## Компоненты

Раскладка по §92.1 гайда: `Core` — кирпичики без знания про сеть, `Content` —
сборщики, `System` — сцена и инфраструктура.

### Контракт ввода

`InputData : INetworkInput` — только блиттируемые поля:

```
Vector2        Move     — нормализованное направление, 8 байт
NetworkButtons Buttons  — битовая маска, бит 0 = Dash
```

`enum InputButton { Dash = 0 }` — значения подряд от нуля, без `[Flags]`:
для `NetworkButtons` значение это **индекс бита**.

### `System`

| Класс | База | Что делает |
|---|---|---|
| `EntryPoint` | MonoBehaviour | UI подключения; `async` `StartGame`, проверяет `result.Ok`, пишет ошибку на экран |
| `InputAccumulator` | MonoBehaviour | подписан на `NetworkEvents.OnInput`; читает `GetAxisRaw` и накапливает Shift между тиками |
| `PlayerSpawner` | MonoBehaviour | `NetworkEvents.PlayerJoined` / `PlayerLeft` под гейтом `IsServer`; `SetPlayerObject` |
| `SpawnPointService` | MonoBehaviour | две точки старта, выдача по индексу команды |

`NetworkEvents` обязан лежать на том же GameObject, что `NetworkRunner` — это
документированный контракт Fusion, а не стиль. Перенесёшь — ввод и спавн молча
перестанут работать.

Подписки — в `OnEnable`, `StartGame` — в `Start`. Unity гарантирует, что
`OnEnable` всех компонентов пройдёт до любого `Start`, поэтому `PlayerJoined`
локального игрока хоста не потеряется.

### `Content`

| Класс | База | Сетевое состояние |
|---|---|---|
| `PlayerMotor` | NetworkBehaviour | `[Networked] NetworkButtons _previousButtons`, `[Networked] TickTimer _dashCooldown` |
| `PlayerIdentity` | NetworkBehaviour | `[Networked] NetworkString<_16> Nick`, `[Networked] int TeamIndex` |
| `Ball` | NetworkBehaviour | нет; только `SetIsSimulated` и host-only `ResetTo` |
| `MatchManager` | NetworkBehaviour | `[Networked] int ScoreLeft/ScoreRight`, `[Networked] TickTimer _goalLockout` |

`PlayerMotor` — единственный шлюз ввода на объект: один `GetInput(out InputData)`
на весь префаб (§92.4). Движение — `linearVelocity = direction * speed` с
сохранением вертикальной компоненты. Даш — `WasPressed(_previousButtons, Dash)`
плюс `TickTimer.ExpiredOrNotRunning` на кулдаун, применяется как единичный
скачок скорости. `_previousButtons` обязан быть `[Networked]`, иначе при
ресимуляции даш сработает дважды.

`PlayerIdentity` красит капсулу и пишет ник на табличку через
`[OnChangedRender]`, начальное значение применяется руками в `Spawned()` —
`OnChangedRender` стреляет только на **изменении**.

### Гол: почему не `OnTriggerEnter`

Гол определяется в `MatchManager.FixedUpdateNetwork()` на хосте: проверка,
попала ли позиция мяча в один из двух AABB ворот. Это чистая функция от
состояния — одинакова на всех пирах и в любом повторе тика.

`OnTriggerEnter` здесь запрещён по тем же причинам, что в гл. 03: колбэк
приходит из цикла Unity-физики, не воспроизводится при ресимуляции и читает
`Physics.defaultPhysicsScene` вместо физической сцены раннера.

Защита от двойного зачёта — `[Networked] TickTimer _goalLockout` на 1.5 с:
пока он не истёк, новый гол не считается. Инкремент счёта идёт под
`HasStateAuthority`, сброс позиций — там же.

Сброс после гола: мяч и обе капсулы телепортируются на стартовые позиции,
скорости гасятся в ноль. Телепорт `NetworkRigidbody3D` — через
`Teleport(position, rotation)` (`INetworkTRSPTeleport`), иначе интерполяция
протащит визуал через всю арену.

### UI

Экран подключения: поле кода комнаты, кнопка «Играть», строка статуса.
Экран матча: счёт `0 : 0` сверху по центру. Legacy uGUI (`Text`, `InputField`) —

## Арена

Коробка 24 × 14 по полу, борта высотой 2. Статические коллайдеры, никаких
Rigidbody. Ворота — проёмы в коротких бортах шириной 6, за ними AABB-зона
зачёта. Камера — перспективная, сверху с небольшим наклоном, вся коробка в кадре,
никакого кода слежения.

## Как это собирается

Unity-проект создаётся и наполняется из командной строки, сцена и префабы —
editor-скриптом, а не правкой YAML руками:

1. `Unity.exe -createProject` на `6000.0.38f1`.
2. Импорт `photon-fusion-2.1.3-stable-2390.unitypackage` через `-importPackage`.
3. Игровые скрипты пишутся как обычные файлы в `Assets/Game/Scripts`.
4. `Assets/Editor/ArenaBuilder.cs` — статический метод, вызываемый через
   `-executeMethod`: строит сцену, префабы, выставляет `NetworkProjectConfig`,
   `EditorBuildSettings`, `activeInputHandler`.
5. `-buildWindows64Player` на standalone-билд.

`NetworkProjectConfig`, что проверяется явно:

- `Fusion.Addons.Physics` и `Assembly-CSharp` в `AssembliesToWeave` — без первого
  не соткётся `[Networked]` внутри `NetworkRigidbody`, без второго молча умрут
  `INetworkInput` и все свои `[Networked]`.
- `PeerMode = Single`, `PlayerCount = 2`.
- Сцена `Game.unity` в `EditorBuildSettings` под индексом 0 — иначе
  `SceneRef.FromIndex(buildIndex)` не сработает.

## Как играть

Оба запускают билд, вводят **одинаковый** код комнаты, жмут «Играть».
Кто первый — хост. Управление: `WASD` — движение, `Shift` — даш.

Проверка до билда: ParrelSync не ставим, второй экземпляр — через
`-createProject`-независимый запуск собранного билда рядом с редактором.

### Чего всё ещё нет

Управление с клавиатуры в автотестах не проверить — мяч пинался кодом. Что
капсулы ходят по WASD и бьют мяч, подтверждается только тем, что `PlayerMotor`
получает ввод по той же схеме, что проверенный учебный код. Это стоит
проверить руками.

Сознательно не выполнено из 92.13: пункт 12 (настройки в `ScriptableObject` —
четыре числа на префабе не стоят отдельного ассета) и пункт 2 в части
`PlayerMotor`, который пишет `[Networked]` на клиенте-владельце ради
предсказания даша — тот же приём, что у пуль в гл. 03.

### Баг 5: кнопка «Играть» не нажималась

Найден пользователем при живой игре. `StatusText` был сверстан так, что по
локальной Y занимал `-155…-75`, а кнопка — `-131…-75`, то есть надпись
**полностью накрывала** кнопку. `Text` в uGUI по умолчанию `raycastTarget = true`
и создавался позже кнопки, поэтому забирал все клики себе. Кнопка работала,
клик до неё не доходил.

Почему не поймалось раньше: **все** автотесты шли через `-autostart`, который
жмёт кнопку из кода. Путь «живой клик мышью» не проверялся ни разу — классическая
дырка в покрытии, когда тест обходит ровно то место, где баг.

**Решение:** всем подписям `raycastTarget = false` (они не должны ловить клики
в принципе), `StatusText` опущен в `-192…-134`.

**Проверено:** синтетическим кликом Win32 (`SetCursorPos` + `mouse_event`) по
центру кнопки в свежем окне без `-autostart`. Игра вошла в комнату как хост,
счёт `0 : 0`, игрок заспавнен. Теперь в покрытии есть и путь через мышь.

### Баг 6: двое из разных мест не видят друг друга (регионы Photon)

Найден пользователем при реальной игре с другом: оба ввели один код комнаты, оба
вошли, друг друга не увидели. Ошибок на экране не было.

**Причина.** `FixedRegion` в `PhotonAppSettings.asset` был пустой при
`UseNameServer: 1`. По `Assets/Photon/PhotonRealtime/Code/AppSettings.cs:160-165`
это даёт `IsBestRegion == true`: каждый клиент сам пингует регионы и уходит в
ближайший. Имя комнаты уникально **внутри региона**, поэтому `ball` в `eu` и
`ball` в `us` — две разные комнаты, и `GameMode.AutoHostOrClient` делает хостом
каждого. Отсюда и «ошибок нет, оба в игре, друг друга нет».

Почему локальные тесты этого не ловили: два процесса на одной машине пингуют из
одной сети, попадают в один регион и соединяются. Баг существует только при двух
разных сетевых путях — то есть ровно в том сценарии, который нельзя проверить на
одном компьютере без VPN.

**Решение.**
1. `FixedRegion: eu` и `AppVersion: 0.1` в `PhotonAppSettings.asset`.
2. `EntryPoint` строит копию глобальных настроек и подменяет регион:
   `PhotonAppSettings.TryGetGlobal(out var g)` → `g.AppSettings.GetCopy()` →
   `settings.FixedRegion = region` → `StartGameArgs.CustomPhotonAppSettings`.
   Копия, а не сам объект: глобальный ассет один на процесс.
   Аргумент `-region <код>` позволяет переключать регион, не правя ассет.
3. Имя комнаты приводится к нижнему регистру: имена сессий Photon
   регистрозависимы, и `Ball` против `ball` — вторая независимая причина
   «разных комнат».
4. Убрана тихая подстановка дефолтной комнаты `ball` при пустом поле: игрок
   молча уезжал в чужую комнату. Теперь просьба ввести код.
5. На экран выведена строка `комната · регион · роль · игроков N/2` —
   **вне** `ConnectPanel`, иначе её гасит вместе с панелью. Критерий для игрока:
   разные регионы или два «ХОСТ» — вы в разных комнатах.

**Проверено, локально и до конца:**

| тест | что запускалось | результат |
|---|---|---|
| A | `-region sa` | регион в рантайме = `sa` — настройка пересиливает пинг |
| B | `-region euu` | `ShutdownReason.InvalidRegion` на экране — значение доезжает до Name Server |
| C | `eu` + `us`, один код комнаты | **оба «хост»**, `players=1` у каждого — симптом воспроизведён |
| D | `eu` + `eu`, один код комнаты | «хост» + «клиент», `players=2`, `connection=Direct` — фикс работает |

Тест C — главный: он воспроизводит баг пользователя на одной машине, а значит
фикс проверен не на веру.

**Отброшено после адверсариальной проверки** (не чинить):
`AppVersion` (был пуст у обоих, то есть идентичен), NAT и punchthrough (релей —
автоматический фоллбэк; провал дал бы видимый `ConnectionTimeout`, а не свою
комнату), гонка «кто первый хост» (решается сервером атомарно в
`OpJoinOrCreateRoom`), переполнение комнаты (дало бы `GameFull` и
`result.Ok == false`), разные сборки и префабы (матчмейкинг не делят — конфиг
рассылает создатель комнаты; расхождение проявилось бы после входа),
необходимость `JoinSessionLobby` (для коннекта не нужен, и лобби само
регионально), разводка полей UI и спавн игроков.

Браузер комнат сознательно не делался: лобби тоже региональное, поэтому комнату
друга из другого региона он бы всё равно не показал — то есть не помог бы ни
диагностике, ни починке.
